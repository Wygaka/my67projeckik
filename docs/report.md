# Отчет по лабораторной работе N7

## Тема

Инструментальные средства разработки программного обеспечения.

## Цель работы

Освоить принципы проектирования модульной архитектуры, реализовать изоляцию бизнес-логики от внешних систем и закрепить работу с Git: ветвление, слияние, stash, cherry-pick, теги, reflog и bisect.

## Предметная область

Разработан мини-сервис управления заказами. Бизнес-правило: если сумма заказа составляет 5000 рублей или больше, применяется скидка 10%.

## Распределение ролей

- Project Manager: планирование структуры проекта и ведение Git-истории.
- System Analyst: описание бизнес-правил заказа.
- Core Developer: реализация слоев Domain, Use Cases и Infrastructure.
- QA Engineer: подготовка и запуск модульных тестов.

## Архитектура

Проект построен по принципам Clean Architecture.

- `src/domain`: сущности `Order` и `OrderItem`, расчет суммы, скидки и итоговой стоимости. Слой не зависит от базы данных, UI или инфраструктуры.
- `src/use_cases`: сценарий `CreateOrderUseCase` и интерфейс `IOrderRepository`. Use Case зависит от абстракции, а не от конкретной базы данных.
- `src/infrastructure`: реализации репозитория `InMemoryOrderRepository`, `SqliteOrderRepository` и логирующий middleware.
- `src/main.py`: корень композиции, где создаются конкретные зависимости.

```text
main.py -> infrastructure -> use_cases -> domain
                    use_cases -> interfaces -> domain
```

## Практическая реализация

Ключевые файлы:

- `src/domain/models.py`: доменные модели и бизнес-правила.
- `src/use_cases/create_order.py`: сценарий создания заказа.
- `src/use_cases/interfaces.py`: контракт репозитория.
- `src/infrastructure/memory_repo.py`: хранение в памяти.
- `src/infrastructure/sqlite_repo.py`: хранение в SQLite.
- `src/infrastructure/logging_middleware.py`: логирование времени выполнения.
- `tests/`: модульные тесты.

## Работа с Git

В репозитории выполнены базовые и расширенные операции:

- инициализация репозитория;
- создание ветки `feature/payment`;
- merge через `--no-ff`;
- создание annotated tag `v1.0.0`;
- применение stash;
- создание hotfix-коммита;
- cherry-pick исправления в `main`;
- подготовлены команды для моделирования merge conflict, reflog и bisect.

Команды и пояснения находятся в `docs/git_commands.md`.

## Ответы на контрольные вопросы

1. Dependency Rule означает, что зависимости исходного кода направлены внутрь: инфраструктура может зависеть от use cases и domain, но domain не должен зависеть от внешних механизмов.
2. Доменный слой не должен импортировать ORM или SQL-драйверы, потому что он хранит бизнес-правила и должен оставаться независимым от способа хранения данных.
3. DIP позволяет use cases работать через абстрактный интерфейс репозитория. Файл `interfaces.py` задает контракт, который реализуют внешние адаптеры.
4. Composition Root - место, где создаются конкретные реализации и связываются зависимости. В проекте это `src/main.py`.
5. Изоляция доменной логики упрощает тестирование: расчеты можно проверять без базы данных, веб-сервера и внешних сервисов.
6. Working Directory - файлы на диске, Staging Area - подготовленные изменения, Repository - хранилище коммитов.
7. `.gitignore` содержит шаблоны игнорирования. Префикс `!` отменяет игнорирование для конкретного файла.
8. `--no-ff` создает отдельный merge-коммит и сохраняет видимую историю ветки.
9. Lightweight tag - простая ссылка на коммит, annotated tag хранит автора, дату и сообщение.
10. `git stash` нужен для временного сохранения незавершенных изменений. `git stash pop` возвращает изменения и удаляет запись из stash.
11. `git reset` перемещает указатель ветки и может переписать историю, а `git revert` создает новый коммит, отменяющий изменения.
12. `git merge` объединяет ветки, сохраняя структуру истории. `git rebase` переносит коммиты на новую базу и делает историю линейной.
13. Конфликт слияния возникает, когда разные ветки изменили одни и те же строки. Нужно открыть файл, выбрать правильный вариант, убрать маркеры, выполнить `git add` и `git commit`.
14. `git reflog` фиксирует перемещения HEAD. Потерянное состояние можно восстановить по записи вида `HEAD@{n}` или по хешу.
15. `git bisect` бинарным поиском находит коммит, который внес ошибку, между известным рабочим и сломанным состоянием.

## Заключение

В ходе работы реализован сервис с разделением ответственности по слоям, применена инверсия зависимостей, добавлены автоматические тесты и подготовлена Git-история с профессиональными командами. Проект можно открыть в VS Code, запустить и защитить по структуре лабораторной работы.
